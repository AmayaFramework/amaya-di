Thank you for your interest in amaya-di! This file describes how to contribute—whether it’s a pull request,
creating a third-party module, or discussing features. You can create your own implementation of a schema factory,
stub factory, or build an alternative to the `amaya-di` module (see 
[creating third-party modules](#creating-third-party-modules)), or make a pull request to 
[this repository](https://github.com/AmayaFramework/amaya-di) (see [creating a pull request](#creating-a-pull-request)).

Each option will be described in detail below. However, first we list the main principles, which are strongly recommended
when developing third-party modules and required for submitting a pull request.

## Core Principles

amaya-di is a modern DI framework focused on reliability, high performance, and minimalism.
Therefore, we adhere to the following principles:

* We value a careful balance between clean, readable code and performance:
    * avoid creating unnecessary entities;
    * if some part of the code is non-obvious, add a comment whenever possible;
    * the public API exposed to users should be as convenient, self-explanatory, and flexible as possible;
    * sacrificing an explicitly controlled and well-integrated API for hidden magic, global containers, or
      annotations is a path to ruin—such changes will never be accepted.
* Any changes must solve a real problem, or improve stability, performance, or readability.
  We don’t need features for the sake of features.
* Discussion of architectural decisions and/or feature criticism is highly encouraged—as long as it stays constructive.
* The minimum supported JDK version is 11. PRs porting to lower versions will be rejected.
* We aim to minimize and limit external dependencies:
    * do not add a library just for a single function;
    * including `guava`, `apache-commons`, or other large packages will result in PR rejection
      (this does not apply to slimmed-down or modular versions containing only used functionality);
    * do not embed implementations of other DI APIs into `amaya-di` or its core modules—use separate modules for this;
    * if a feature can be implemented with the Java SDK in a reasonable time and with acceptable quality,
      avoid using external libraries.
* Changes to the public API must preserve its general-purpose nature. Tweaking it to suit a single feature at the
  cost of everything else is not acceptable.
* If you want to make a small fix or improvement, please submit a PR rather than creating a fork or republishing
  the package under the same name. This helps keep the ecosystem clean and avoids confusion.
* If your feature involves bytecode generation:
    * avoid using large, "smart", and/or slow libraries (like `bytebuddy`)—our choice is
      plain `org.ow2.asm:asm` or [Class-File API](https://openjdk.org/jeps/484);
    * do not use Java agents or bytecode transformation of loaded classes—this is not supported on many JVMs;
    * if possible, ensure that your generation algorithm is efficient and performs within acceptable limits;
    * ensure that the generated bytecode is optimized and runs efficiently—optimizations are always welcome;
    * if possible, ensure that your bytecode does not depend on JVM internal state and can be reloaded after restart:
        * use only stable values for descriptors and names;
        * if data order matters, use collections with stable order (e.g., `TreeMap`);
        * if independence cannot be achieved, document this explicitly.

## Creating Third-Party Modules

amaya-di is a meta-project including core modules (core, schema, stub) and a unifying wrapper.
All modules are published as standalone JPMS modules and Maven artifacts.
This allows you to include only the parts of the framework you actually need.

A third-party module should be developed in a separate Java (or any JDK language) project and in a separate repository.
However, if you believe your module implements base functionality or is general enough to be included in the core set,
submit a PR with a Gradle module (to do this, add `include '<your_module_name>'` in `settings.gradle`, create a
directory in the project root with the same name, add `build.gradle` and the corresponding `src` directories inside it).

After creating your project, you need to set up dependencies. `amaya-di` follows a delivery principle similar to
`jakarta`:

* each logical module is separated into a JPMS module published to Maven Central;
* modules provide public API (mostly interfaces and base utilities);
* module implementations are provided by the framework itself, and third-party modules depending on them should
  declare them as `compileOnly`.

You can refer to the [asm](../../asm/build.gradle) and [reflect](../../reflect/build.gradle)
implementations as examples.

The set of modules to include depends on the feature you're implementing. Decide which part of the API you need
and include the corresponding modules. Please also pay attention to dependency scopes.

* `amaya-di-core`: `ObjectFactory`, `TypeProvider`, `TypeRepository`, `ServiceProvider`, and their implementations (see README);
* `amaya-di-schema`: `ClassSchema` (and its variants), `SchemaFactory` and its implementation (see README);
* `amaya-di-stub`: `CachedObjectFactory`, `CacheMode`, `StubFactory` (+ core and schema types);
* `amaya-di`: all three modules + builder API.

Next, implement your desired functionality and design how the user will interact with it (the “entry point” to the API).
Be sure to cover all code involved in container assembly and operation with tests.
If you wish, you may publish your library to Maven Central (see the framework's configuration or contact me if
you encounter technical issues).

I’d be happy if you open a pull request or an issue with a link to your implementation so we can include it in
the documentation.

## Creating a Pull Request

### Getting Started

1. Fork the repository.
2. Create a new branch with a descriptive name: `feature/feature-name` or `bugfix/bug-description`.
3. Write code that matches the existing style, architecture, and the [principles](#core-principles) described above.
4. Add tests if none yet exist for your changes.
5. Provide a detailed explanation of your changes.
6. Open a pull request.

### Code Requirements

* Code must be readable and follow good OOP practices.
* Do not add platform- or JVM-specific hacks.
* Core functionality should be covered by tests (both positive and negative scenarios).
* Only the JDK version used by the project is allowed (currently 11).
* If changes affect core modules, only Java is allowed.
* If you’re creating a new module or modifying a module in another language, any JVM language (11+) or the module's original language is acceptable.

### Communication

* Pull requests must have a clear description: what, why, and how.
* Questions and suggestions should go through [issues](https://github.com/AmayaFramework/amaya-di/issues).
* Rudeness or toxicity is grounds for closing a PR/issue without discussion.
* We don’t guarantee quick feedback. This project is developed in free time.

### Branches and Releases

* The `main` branch always reflects the latest stable major release.
* `release/<major>.<minor>` branches are stable and contain tags for minor updates.
* Feature branches and bugfixes go into separate branches.
* To be accepted, a PR must compile, pass tests, and go through review.

## What Is NOT Welcome

- Violating the framework's core principles.
- Changes without tests.
- Introducing complex features without justification.
- Style changes without cause.
- Large refactorings without prior discussion.
