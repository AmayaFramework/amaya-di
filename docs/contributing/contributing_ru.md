Спасибо за интерес к amaya-di! В этом файле описано, как внести вклад — будь то pull request, 
создание стороннего модуля или обсуждение фич. Вы можете создать свою реализацию фабрики схем внедрения, 
фабрики stub'ов, собрать аналог модуля `amaya-di` (см. [создание сторонних модулей](#создание-сторонних-модулей) 
или сделать pull request в [этот](https://github.com/AmayaFramework/amaya-di) репозиторий 
(см. [создание pull request](#создание-pull-request)).

Каждый вариант будет подробно рассмотрен ниже. Однако для начала перечислим основные принципы, соблюдение которых 
крайне рекомендовано при разработке сторонних модулей и обязательно для вливания pull request'а.

## Основные принципы

amaya-di — это современный DI-фреймворк, ориентированный на надёжность, высокую производительность и минимализм. Поэтому
мы придерживаемся нижеописанных принципов.

* Мы ценим осторожный баланс между чистым и понятным кодом и быстродействием:
  * не следует плодить лишние сущности;
  * если какая-либо часть кода неочевидна сама по себе, следует по возможности прокомментировать её;
  * публичное API, доступное пользователям, по возможности должно быть максимально удобным, самодокументированным и гибким;
  * отказ от явно контролируемого и хорошо встраиваемого API в пользу неявной магии, глобальных контейнеров и 
  аннотаций — прямой путь к смерти, такие изменения никогда не будут одобрены.
* Любые изменения должны решать существующую проблему, улучшать стабильность, производительность или читаемость. Нам не
нужны фичи ради фич.
* Предварительное обсуждение архитектурных решений и/или критика функционала горячо приветствуются. До тех пор, пока они
проходят в конструктивной форме.
* Минимальный уровень jdk — 11. PR с портами на более низкие версии будут отклонены.
* Мы придерживаемся политики минимизации и максимального сокращения используемых зависимостей:
  * не следует добавлять библиотеки ради одной функции;
  * наличие `guava`, `apache-commons` и других монструозных пакетов автоматически приведет к отклонению PR (тем не 
  менее, это не относится к их обрезанным/модульным версиям, содержащим только используемый функционал);
  * не следует встраивать в `amaya-di` и его базовые модули реализации других DI API, для этого есть отдельные модули;
  * если требуемую фичу можно реализовать с помощью Java SDK за адекватное время и на приемлемом уровне качества, 
  не следует использовать сторонние зависимости.
* Вносимые изменения в публичное API должны сохранять его универсальность. Приведение к виду, удобному для конкретной
фичи в ущерб всему остальному не допускается.
* Если вы хотите внести небольшое исправление или улучшение, пожалуйста, отправьте PR, а не создавайте форк/переиздание 
пакета под тем же именем. Это помогает сохранить экосистему чистой и предотвращает путаницу.
* Если вы хотите реализовать фичу, основанную на генерации байт-кода:
  * откажитесь от использования медленных, "умных" и/или больших библиотек (`bytebuddy` и т.д.); наш выбор —
  чистый `org.ow2.asm:asm` или [Class-File API](https://openjdk.org/jeps/484);
  * не используйте java agents и механизмы изменения загруженного байт-кода — этот функционал доступен далеко 
  не на всех JVM;
  * по возможности убедитесь, что ваш алгоритм генерации достаточно оптимален и работает за адекватное время;
  * убедитесь, что сгенерированный байт-код оптимален и работает за адекватное время — оптимизации здесь 
  никогда не бывают лишними;
  * по возможности убедитесь, что ваш байт-код не зависит от внутреннего состояния JVM и может быть загружен после
  перезапуска без изменений:
    * используйте для дескрипторов и имён только стабильные данные;
    * если при передаче данных важен их порядок, убедитесь, что используются коллекции со 
    стабильным порядком (например, `TreeMap`);
    * если по какой-либо причине добиться независимости не получилось, обязательно упомяните об этом в документации.

## Создание сторонних модулей

amaya-di — это метапроект, включающий в себя базовые модули (core, schema, stub) и их объединяющую оболочку. 
Все модули публикуются как независимые JPMS-модули и Maven-артефакты. 
Это позволяет подключать только нужные части фреймворка.

Разработка стороннего модуля осуществляется в отдельном java- (или любом другом языке JDK) проекте и в отдельном 
репозитории. Однако, если вы считаете, что ваш модуль реализует базовый или достаточно общий для включения в основной
набор функционал, создавайте PR с gradle-модулем (для этого необходимо добавить в settings.gradle 
`include '<your_module_name>'`, создать директорию в корне проекта с соответствующим именем, добавить в нее 
`build.gradle` и соответствующие поддиректории `src`).

Далее, после создания проекта, необходимо установить зависимости. `amaya-di` использует принцип поставки, схожий с 
принятым в `jakarta`:

* каждый логический модуль вынесен в отдельный JPMS-модуль, опубликованный в пакете maven central;
* модули поставляют публичное API (в основном интерфейсы и базовые утилиты);
* тела модулей предоставляются самим фреймворком, а сторонние модули, зависящие от них, подключают их как `compileOnly`.

В качестве примера вы можете использовать [asm](../../asm/build.gradle) и [reflect](../../reflect/build.gradle) 
реализации. 

Набор устанавливаемых модулей зависит от того, какую именно фичу вы хотите реализовать. Решите, какая именно часть API
фреймворка вам нужна, и подключите соответствующие модули. Также, пожалуйста, следите за областью видимости ваших
зависимостей.

* `amaya-di-core`: `ObjectFactory`, `TypeProvider`, `TypeRepository`, `ServiceProvider`, их реализации (см. readme);
* `amaya-di-schema`: `ClassSchema` (и её разновидности), `SchemaFactory` и её реализация (см. readme);
* `amaya-di-stub`: `CachedObjectFactory`, `CacheMode`, `StubFactory` (+ core и schema типы);
* `amaya-di`: все три модуля + builder-API.

Далее реализуйте желаемый функционал и продумайте механизм, с помощью которого конечный пользователь будет получать 
к нему доступ ("точку входа" в API). Обязательно покройте тестами код, участвующий в сборке и работе контейнера.
Если хотите, опубликуйте вашу библиотеку в maven central (в случае технических трудностей изучите конфигурацию 
фреймворка или свяжитесь со мной).

Буду рад, если после публикации вы создадите pull request или напишите issue с предложением добавить ссылку 
на вашу реализацию в документацию.

## Создание pull request

### Как начать

1. Форкните репозиторий.
2. Создайте новую ветку с понятным названием: `feature/<feature-name>` или `bugfix/<bugfix-description>`.
3. Пишите код, ориентируясь на существующий стиль, архитектуру и вышеописанные [принципы](#основные-принципы).
4. Покройте изменения тестами, если таковых ещё нет.
5. Приложите в свободной форме подробное описание изменений.
6. Сделайте Pull Request.

### Требования к коду

* Код должен быть читабельным и следовать хорошим практикам ООП.
* Не надо добавлять платформо- и jvm- зависимые решения.
* Основной функционал должен быть покрыт тестами (как позитивные, так и негативные сценарии).
* Допускается только та версия JDK, которая используется в проекте (сейчас 11).
* Если это изменения в уже существующие основные модули, допускается только Java.
* Если это новый модуль/изменения в модуль на другом языке, допускается любой JVM-язык (11+)/оригинальный язык модуля.

### Общение

* Pull Requests должны иметь понятное описание: что, зачем и как.
* Вопросы и предложения — через [issues](https://github.com/AmayaFramework/amaya-di/issues).
* Негатив (грубость или переход на личности) и/или токсичность — причина закрытия PR/issue без обсуждения.
* Мы не гарантируем быструю обратную связь. Проект развивается в свободное время.

### Ветки и релизы

* Ветка `main` всегда в состоянии последнего стабильного мажорного релиза.
* Ветки `release/<major>.<minor>` стабильны и содержат теги, отмечающие минорные обновления.
* Фича-ветки и багфиксы — в отдельные ветки.
* Для принятия PR код должен компилироваться, проходить тесты и пройти ревью.

## Что НЕ приветствуется

- Нарушение основных принципов фреймворка.
- Изменения без тестов.
- Добавление сложных фич, если они не обоснованы.
- Изменения стиля без причины.
- Большие рефакторинги без предварительного обсуждения.
