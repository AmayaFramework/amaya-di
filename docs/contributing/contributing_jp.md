amaya-di に関心をお寄せいただきありがとうございます！このドキュメントでは、pull request の作成、サードパーティーモジュールの開発、または機能の提案・議論など、amaya-di への貢献方法について説明します。  
スキーマファクトリやスタブファクトリの独自実装、`amaya-di` に類似したモジュールの開発（[サードパーティーモジュールの作成](#サードパーティーモジュールの作成) を参照）や、[こちらのリポジトリ](https://github.com/AmayaFramework/amaya-di) への pull request の提出（[pull request の作成](#pull-request-の作成) を参照）などが可能です。

各方法については、以下で詳しく説明します。ただし最初に、サードパーティーモジュールを開発する際に強く推奨される、また pull request に必須となる基本原則を紹介します。

## 基本原則

amaya-di は、信頼性・高性能・最小主義を重視した現代的な DI フレームワークです。そのため、以下の原則に従っています。

* 明快かつ効率的なコードのバランスを大切にします：
    * 不必要な抽象や構造は追加しないこと；
    * 読みにくいコードには可能な限りコメントを追加すること；
    * パブリック API は可能な限り使いやすく、自己説明的で柔軟であること；
    * 明示的に制御・拡張可能な API を、隠れた魔法的な仕組み、グローバルコンテナ、アノテーションなどで置き換えることは禁止します。
* すべての変更は、既存の問題の解決、安定性・性能・可読性の向上につながる必要があります。単なる機能追加は不要です。
* アーキテクチャに関する議論やフィードバックは歓迎します（建設的である限り）。
* 最低サポート JDK バージョンは 11 です。それ未満を対象とした PR は受け付けません。
* 依存関係の最小化を原則とします：
    * 単一の関数のためにライブラリを追加しないこと；
    * `guava`、`apache-commons` などの巨大なパッケージの使用は原則拒否されます（ただし、必要最小限の機能のみを含む軽量版は除く）；
    * 他の DI API の実装を `amaya-di` 本体に組み込まないこと。別モジュールで行ってください；
    * Java SDK で妥当な時間と品質で実装できる場合、外部ライブラリの使用は避けてください。
* 公開 API への変更は、汎用性を損なわないようにすること。特定の機能に特化しすぎた実装は許可されません。
* 小さな修正や改善であれば、パッケージを fork して再配布するのではなく、PR を送ってください。これによりエコシステムの一貫性が保たれ、混乱が避けられます。
* バイトコード生成を伴う機能を追加したい場合：
    * 遅くて重い「スマート」なライブラリ（例：`bytebuddy`）の使用は禁止です。当プロジェクトでは、純粋な `org.ow2.asm:asm` または [Class-File API](https://openjdk.org/jeps/484) を推奨します；
    * Java Agent やロード済みバイトコードの変更は、多くの JVM 環境で使用できないため禁止です；
    * 生成アルゴリズムのパフォーマンスが十分であることを確認してください；
    * 生成されたバイトコードの最適化を行い、適切なパフォーマンスが得られること；
    * バイトコードが JVM の内部状態に依存せず、再起動後でも安定してロード可能であることを確認してください：
        * デスクリプタや名前には安定したデータのみを使用；
        * データの順序が重要な場合は、順序が保証されたコレクション（例：`TreeMap`）を使用；
        * どうしても独立性が得られない場合は、必ずドキュメントに明記してください。

## サードパーティーモジュールの作成

amaya-di はメタプロジェクトであり、基本モジュール（core、schema、stub）とそれらを統合するラッパーから構成されています。  
すべてのモジュールは、独立した JPMS モジュールおよび Maven アーティファクトとして公開されています。  
これにより、必要な部分だけを導入できます。

サードパーティーモジュールの開発は、別の Java プロジェクト（または他の JDK 言語）および独立したリポジトリで行ってください。  
ただし、そのモジュールが基本的または汎用的な機能を提供する場合は、Gradle モジュールとして PR を作成することが可能です（`settings.gradle` に `include '<your_module_name>'` を追加し、プロジェクトルートに対応するディレクトリ、`build.gradle`、および `src` サブディレクトリを作成してください）。

次に、依存関係を設定します。`amaya-di` は `jakarta` のような供給モデルに従っています：

* 各論理モジュールは独立した JPMS モジュールで、maven central に公開されています；
* モジュールは主にインターフェースやユーティリティとしてパブリック API を提供します；
* モジュール本体はフレームワークが提供し、外部モジュールはそれらを `compileOnly` で参照します。

例としては、[asm](../../asm/build.gradle) や [reflect](../../reflect/build.gradle) の実装をご覧ください。

導入するモジュールは、実装する機能に応じて決定します。  
必要な API を選び、対応するモジュールを追加してください。依存範囲にも注意してください。

* `amaya-di-core`: `ObjectFactory`, `TypeProvider`, `TypeRepository`, `ServiceProvider` など（README 参照）；
* `amaya-di-schema`: `ClassSchema` およびその派生、`SchemaFactory`（README 参照）；
* `amaya-di-stub`: `CachedObjectFactory`, `CacheMode`, `StubFactory`（core と schema 型を含む）；
* `amaya-di`: 上記すべての統合と builder API。

その後、実装した機能をどのようにユーザーに公開するか（API の「エントリーポイント」）を設計してください。  
コンテナの構築や実行に関わるコードは、必ずテストを追加してください。  
maven central への公開を希望する場合は、設定を参考にするか、お気軽にご連絡ください。

公開後、pull request を送るか、issue でドキュメントへのリンク追加を提案していただけると幸いです。

## pull request の作成

### 開始方法

1. リポジトリをフォークする。
2. 分かりやすい名前の新しいブランチを作成：`feature/<feature-name>` や `bugfix/<bugfix-description>`。
3. 既存のコードスタイル、設計、および [基本原則](#基本原則) に従って実装。
4. テストがなければ追加してください。
5. 変更内容の詳細な説明を添えてください（形式は自由）。
6. Pull Request を作成。

### コード要件

* コードは読みやすく、良好な OOP の実践に従っていること。
* プラットフォーム／JVM 固有の実装は避けてください。
* 主要な機能にはポジティブ・ネガティブ両方のテストを付けること。
* 対応 JDK バージョンはプロジェクトで使用されているもの（現在は 11 のみ）。
* 既存の主要モジュールの変更は Java のみ許可されます。
* 新モジュールや他言語のモジュールの場合、任意の JVM 言語（11+）や元の言語が使用可能です。

### コミュニケーション

* Pull Request には「何を」「なぜ」「どうやって」行ったかを明記してください。
* 質問や提案は [issues](https://github.com/AmayaFramework/amaya-di/issues) からどうぞ。
* 無礼・人格攻撃・有毒な発言は、予告なく PR や issue をクローズする理由となります。
* 本プロジェクトは空き時間に開発されており、迅速な返信は保証されません。

### ブランチとリリース

* `main` ブランチは常に最新の安定メジャーリリースを示します。
* `release/<major>.<minor>` ブランチは安定版であり、マイナー更新のタグを含みます。
* 機能や修正は別ブランチで管理されます。
* PR の受理には、コードがコンパイル可能で、テストに合格し、レビューを通過する必要があります。

## 推奨されないこと

- フレームワークの基本原則に反する変更。
- テストなしの変更。
- 根拠のない複雑な機能追加。
- 理由のないコードスタイル変更。
- 事前相談のない大規模リファクタリング。
